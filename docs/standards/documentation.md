# Documentation

Docs are part of the change. A pull request that changes behaviour or a
command and leaves the docs behind isn't done.

## Where things are written

| Kind | Where | Written for |
|---|---|---|
| **How the platform works** | [`docs/handbook/`](../handbook/README.md) | Someone new to the project |
| **The rules** | [`docs/standards/`](README.md) | Anyone changing the code |
| **What a folder builds** | A `README.md` in every Terraform folder | Someone about to use or change that folder |
| **How to do a task** | [`runbooks/`](../../runbooks/README.md) | Someone at a terminal, step by step |
| **Why a decision was made** | [`docs/decisions/`](../decisions/README.md) | Someone about to undo it |
| **Proof it works** | [`docs/deliverables/evidence.md`](../deliverables/evidence.md) and `infrastructure/**/evidence/` | Reviewers and assessors |
| **What changed** | [`CHANGELOG.md`](../../CHANGELOG.md) | Anyone catching up |

Say a thing in one place and link to it from the others. A fact written in
two places will eventually disagree with itself.

## Folder READMEs

Every Terraform folder has a README with these parts, in this order:

1. **Title** with the folder name in backticks: `# Network (`network`)`.
2. **What it builds:** one or two sentences in plain English.
3. **Used by:** which solutions and root configs.
4. **What you get:** a table of the parts and why each is there, with
   Guide or benchmark references.
5. **Good to know:** trade-offs, costs and gotchas.
6. **Usage** (modules): the real call from this repository, copied, not made
   up.
7. **Reference** (modules): generated by terraform-docs between
   `<!-- BEGIN_TF_DOCS -->` and `<!-- END_TF_DOCS -->`. Don't edit inside
   the markers.

Root config READMEs say what the root config contains, what you fill in
(the settings file), how it differs between environments or solutions, and
which runbook to follow, in place of Usage and Reference.

### Generated reference

The inputs, outputs, requirements and providers tables come from the code,
so they're always complete. That's also why every variable and output needs
a good description ([Variables and outputs](variables-and-outputs.md)).

```powershell
# After changing a module's variables or outputs, in that module's folder:
terraform-docs -c ../.terraform-docs.yml .
```

Install with `winget install Terraform-docs.Terraform-docs` (version 0.24).
CI's **Module READMEs** job fails if any reference is out of date. The
settings are in [`infrastructure/modules/.terraform-docs.yml`](../../infrastructure/modules/.terraform-docs.yml).

## Decision records

A decision with lasting consequences gets an ADR in `docs/decisions/`, with
the next number: context, options weighed, decision, consequences, and when
to revisit it. Records are never deleted; a superseded one is marked as such
and keeps its reasoning. Add it to the table in
[`docs/decisions/README.md`](../decisions/README.md).

## Evidence

- Every deployment run is logged to a dated file and recorded in the
  [evidence log](../deliverables/evidence.md#evidence-log) with its resource
  counts and timings.
- Screenshots go in `docs/media/screenshots/`, numbered, and are **redacted
  first**: account IDs, organisation IDs, email addresses, student numbers,
  sign-in names and ARNs.
- Status words are used exactly: **demonstrated** (ran in AWS),
  **configured** (in code, not yet run live), **designed** (written down
  only), **enforced** (a guardrail stops anyone turning it off). Don't call a
  control working when it only exists in code.

## Style

- Plain English for someone outside the team. Explain an AWS term the first
  time, or link the [glossary](../handbook/glossary.md).
- Short sentences. Tables for anything with more than two attributes.
- Australian English and AUD. Dates as "18 October 2026"; sprint and meeting
  records use QUT weeks.
- Relative links within the repository, so they work on any branch. Check
  them before pushing.
- Every page starts with a sentence saying what it's for.
